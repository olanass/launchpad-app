## Review status

An independent security audit of the launchpad and durable-order flow is not documented here. Automated tests, source verification, and a successful build are not independent audits.

Token contract source verification is separate from application security. See [Contract and networks](/token/contract-and-networks) for the token reference.

## Implemented safeguards

- Creator signatures bind API listing creation and management actions.
- Endpoint checks reject local and private-network destinations and pin validated DNS addresses.
- Payment verification checks network, successful receipt, confirmations, payer, recipient, asset, and amount.
- Durable approvals bind the exact request and versioned quote.
- Order state and payment redemptions are stored durably to prevent duplicate purchase processing.
- Production disables demo payment proofs.
- Order responses use private access credentials and no-store caching.

## Operational limits

Projects remain responsible for their upstream API, data, uptime, and input validation. A catalog listing does not guarantee the quality or safety of its result.

An onchain payment may confirm even when the upstream returns an error. If execution becomes ambiguous after a timeout or crash, the order is not automatically replayed. Arbitrary third-party services cannot be promised exactly-once execution.

Production needs durable database configuration. File-paywall assets have additional storage and vault-secret requirements; the file store should not be confused with the API catalog and order database.

## Reporting an issue

Do not publish wallet secrets, order access tokens, private approval links, or paid response data in a public issue. Share a minimal reproduction with secrets removed through a verified project contact.

For integration testing, use isolated fixtures and mocked payments first. A funded wallet transaction is a separate check from passing the automated test suite.
